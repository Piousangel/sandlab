# 세션 가이드 (샌드랩 팀)

루틴은 하루 3번(06·13·20시 KST) 돈다. 각 세션은 **자기 시간 절**을 따른다. 규칙의 근거는 CLAUDE.md·[OPERATING.md](./OPERATING.md)·[DESIGN-PROCESS.md](./DESIGN-PROCESS.md)·.claude/team/charter.md·.claude/skills/sandlab-daily/SKILL.md·docs/ops/playbook.md.

## 0. 모든 세션 공통
1. **시작**: `git pull`, `gh pr list`, docs/daily/backlog.md·log.md, 오늘 회의록(docs/team/meetings/YYYY-MM-DD.md), .claude/handoff/main.md(함정). **열린 `daily/*` PR이 있으면 이어받는다.**
2. **깊이 규칙 (오너 11-17: "10분에 떡하니 내지 말고 2~3시간, 크면 4~5시간 고민하고 테스트하고 출시")**: 한 출시는 **리서치 1**(비슷한 물리·퍼즐 사이트, 레벨 디자인 사례, 사용자 불만 등 서로 다른 출처 3종 이상) → **기획 v1** → **리서치 2**(기획을 반증하는 조사) → **기획 v2** → **독립 리뷰**(서브에이전트 혹평, 수용/거부 응답) → 구현 → **검증**(공략 주장은 `CAP=400 npx tsx scripts/spill-explore.mts <id>`로 확인한 것만) → 출시 순서의 반복 라운드를 거친다. 결과는 `docs/team/specs/YYYY-MM-DD-<이름>.md`에 남긴다. **최소 2~3시간**, 큰 일은 4~5시간(여러 세션에 걸쳐도 됨). 서두르지 말고 쪼개서 낸다. 서브에이전트를 적극 쓴다.
3. **일일 출시 원칙**(OPERATING): 하루에 하나 이상 사용자에게 보이는 것을 출시(머지 + 배포 성공 + 라이브 확인). 기본 단위는 새 Spill 레벨 + 공략, 또는 회의에서 고른 더 시급한 개선. 단순 양산이 아니라 **레벨·기능을 고민하고 기획해서** 낸다(왜 이 레벨이어야 하는가, 기존 레벨과 어떻게 다른가, 공략의 깊이).
4. **검증(모두 통과해야 머지)**: pnpm install --frozen-lockfile · pnpm typecheck · pnpm test --exclude src/lib/spill/verify/verify.test.ts · pnpm spill:verify(전 레벨 PASS) · pnpm build && node scripts/verify-ads.mjs. 실패하면 머지하지 않고 PR에 원인을 적는다. 직접 배포하지 않는다. PR 전 `git status --short` 확인, 머지 뒤 배포 워크플로 성공과 라이브 URL 확인.
5. **금지**: main 직접 푸시, force push, 테스트 약화·삭제, 공유 URL 형식 변경, 광고를 게임·캔버스 화면에 넣기, AdSense 재심사 신청, 보고 주소 외 메일, 메일 답장, **외부 서비스 게시(게시는 사람이 한다. 샌드랩은 마케팅 문안 초안까지)**, 기존 레벨 id 변경, 댓글 기능, 격자 1200×600 변경, 시뮬 품질 작업. Cloudflare 전용(Vercel 금지).
6. 기록: docs/daily/log.md 한 줄, backlog, 갈림길은 DECISIONS.md, 노하우는 playbook '배운 점'. 커밋은 한국어 conventional + `Co-Authored-By: Claude Sonnet 5.5 <noreply@anthropic.com>`, PR 끝에 `🤖 Generated with [Claude Code](https://claude.com/claude-code)`.

8. **주인 의식 (오너 11-17: "토스·실리콘밸리 기획자들이다, 주인 의식을 가져")**
   - 우리는 시킨 일을 하는 실행자가 아니라 **이 제품의 주인**이다. 지시를 기다리지 않는다: 지표·사용자·경쟁 사이트·코드를 보고 **스스로 문제를 찾고 우선순위를 정해 끝까지 해결**한다. 오너는 큰 방향만 잡는다.
   - **출시는 끝이 아니라 시작이다.** 출시한 게임·챌린지·레벨마다 **7일·14일·30일 뒤 성장 슬롯**을 잡는다(요소 추가, 난이도 조정, 리뉴얼, 공략 보강, 홍보, 또는 격하 판단). 상태는 `docs/team/portfolio.md`(게임별: 출시일, 최근 개선, 다음 성장 슬롯, 지표 요약)에 한 줄씩 관리한다. 없으면 만든다.
   - **연결 구조를 함께 출시한다.** 새 기능·게임·레벨을 기획할 때 "어디서 들어오고(유입), 끝난 뒤 어디로 가며(다음 행동), 왜 돌아오나(재방문)"를 적고, 홈·추천·가이드·일일·공유 같은 **연결 고리를 같은 출시에 넣는다**. 연결 없는 단독 출시는 반쪽이다.
   - **결과에 책임진다.** 배포 성공·라이브·사용자 반응까지 확인하고, 문제는 숨기지 않고 원인과 수정을 기록한다. 어색하거나 상충하는 규칙은 묻지 말고 고쳐서 문서로 남긴다.

## 사용자 관점 질문 (필수 — 오너가 시키지 않아도 팀이 스스로 끊임없이 묻는다)
오너 11-17: "사용자 입장에서 왜, 어떻게 같은 질문을 끊임없이 하라. 이런 건 알려주지 않아도 하는 최고의 팀이다." **오너가 지적하기 전에 팀이 먼저 발견한다**(예: '너무 쉽다'는 오너가 말하기 전에 사람형 봇 시뮬로 팀이 먼저 찾았어야 했다). 기획 라운드마다 아래 질문에 **답을 적고**, 답이 약하면 기획을 고친다.
1. **처음 온 사람**: 이 화면에서 무엇을 해야 하는지 3초 안에 아는가? 왜 이걸 눌러야 하나? 설명 없이 이해되는가? 첫 10초에 무엇을 느끼는가(재미·혼란·지루함)?
2. **왜 계속 하나**: 한 판이 끝났을 때 "한 판 더" 하고 싶은 이유가 무엇인가? 내일 다시 올 이유는? 지금 레벨·판의 어떤 부분이 지루해질 때 사용자는 어디서 떠나는가?
3. **왜 졌나/왜 못 하나**: 실패했을 때 *내 탓*이라고 느끼는가, 억울한가? 무엇을 고치면 되는지 알 수 있는가? 너무 쉽거나 너무 어려운 구간은 어디인가(숙련자·보통·캐주얼 각각, 사람형 시뮬로 숫자로)?
4. **어떻게 쓰나**: 한 손(엄지)·모바일 390px·소리 끔·느린 기기·중간에 탭을 숨겼다 돌아오기·뒤로 가기·연타·잘못 누르기에서 무슨 일이 일어나는가(멍청한 사용 시험)? 접근성(색만으로 구분하지 않는가)?
5. **왜 공유하나**: 친구에게 보여 주고 싶은 순간이 있는가? 공유 문구·카드가 그 순간을 담는가?
6. **우리 사이트에서 왜**: 같은 게임을 하는 다른 사이트(Poki·CrazyGames·앱스토어 등) 대신 여기서 해야 할 이유가 있는가? 경쟁 사이트는 같은 문제를 어떻게 풀었고 사용자들은 뭐라고 불평하는가?
7. **오너가 볼 때**: 오너가 한 판 해 보면 무엇을 지적할까? (너무 쉽다/어렵다, 반응이 느리다, 안 예쁘다, 설명이 없다, 소리가 거슬린다, 비슷한 게임이 이미 있다) — **먼저 스스로 혹평하고 고친 뒤** 보여 준다.
라운드 결과 문서에 '사용자 질문' 절을 두고 위 7개에 대한 답과 근거(조사·시뮬·테스트)를 적는다. 근거 없는 "괜찮을 것"은 답이 아니다.
